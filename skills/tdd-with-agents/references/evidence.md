# Evidence

Dated 2026-08-19. This file holds everything volatile and everything that
carries a caveat. Read it before repeating a claim from `SKILL.md` to anyone
else, and before overriding the guidance.

## Sources

**Primary.** Birgitta Böckeler, "TDD inside the agent loop - theater or actual
value?", martinfowler.com, 10 August 2026.
<https://martinfowler.com/articles/exploring-gen-ai/tdd-in-the-agent-loop.html>
Raw session data and per-solution analyses:
<https://github.com/birgitta410/tdd-comparisons>

**Supporting.** Birgitta Böckeler, "Sensors for coding agents",
martinfowler.com. <https://martinfowler.com/articles/sensors-for-coding-agents.html>
Source for the mutation-testing argument and the coverage-is-not-effectiveness
example.

Both are exploratory field reports by a practitioner, not controlled studies,
and both say so.

## The experiment

- Three greenfield tasks (small, medium, large), all pure business logic,
  designed with Claude's help to be idiosyncratic so solutions would vary rather
  than reproduce something dominant in training data.
- Five batches. Each batch ran the same task twice with TDD instructions and
  twice without. One batch added two runs instructed to write tests first
  without full incremental red-green discipline.
- All runs, TDD and non-TDD alike, were instructed to reach at least 80% code
  coverage. The instruction was constant across arms, so coverage is not a
  differentiator. Achieved coverage per solution is not reported.
- Solutions generated with Sonnet 4.6. TDD adherence judged from session
  transcripts by Sonnet 4.6. Solution quality judged by Opus 4.8, blind to how
  each solution was produced, using a rubric it generated on the fly.

## Findings

**No quality benefit from in-loop TDD, and a slight edge against it.** Across
the small and medium tasks, Opus generally ranked the two non-TDD solutions
first and second and the two TDD solutions third and fourth. On the large task,
TDD landed mid-pack while non-TDD runs took both the best and the worst spot.
Overall both approaches produced both a best and a worst solution, with TDD
slightly worse on aggregate.

**One exception, not reproducible.** After the TDD prompt was strengthened with
an explicit refactor-and-design-review step, one TDD solution ranked first. In
the same batch, another run with the identical prompt ranked last. This is the
lead behind the design-review adjustment in `SKILL.md`, and it is a lead only.

**No mutation-score difference.** Mutation scores across solutions showed no
signal that TDD runs produced more effective regression tests. This is the
sharpest result, because test effectiveness is the benefit TDD most directly
claims to guarantee.

**The mechanism, per Opus's post-hoc analysis of the traces.** Non-TDD and
test-first runs built the complete design (architecture, data types, edge cases,
contracts) before writing any code or tests. TDD runs did not, because the
instructions actively work against an up-front design step. Their design emerged
from many locally minimal decisions, was rarely revisited, and tended to settle
on whatever shape the first test happened to lock in. Behavior the agent never
thought to write a test for was never implemented at all. This is a hypothesis
generated by a model reading its own earlier judgments, so it is the least
robust part of the chain even though it is the most useful.

**A theory for why.** Ivett Ördög, quoted in the article: models have seen
overwhelmingly more completed functions paired with descriptions than
step-by-step TDD transcripts, so their internal representation of code is a
direct requirements-to-code mapping rather than a process for arriving at one.

**Agents are unreliable at the ritual.** Across sessions, agents wrote
implementation before tests, skipped or fabricated the red confirmation, and
over-implemented ahead of the current test. The prompt eventually used worked
"well enough" with Sonnet but no session followed TDD perfectly. Every TDD run
needed an independent agent to judge adherence from the transcript, precisely
because self-report could not be trusted.

## Coverage is not effectiveness

From the sensors article, a concrete case: a `mappers.ts` file reported 100%
statement coverage and 75% branch coverage while having no unit tests at all.
Coverage came entirely from one broad acceptance test that happened to call
through it. Stryker reported 13 surviving mutants. Coverage recorded that the
lines ran; nothing verified what they produced.

The same article notes that the industry drift toward acceptance-test-heavy
suites makes this worse, because acceptance tests raise coverage while being
comparatively assertion-light.

## Caveats

State these whenever the findings are repeated.

- Very small sample. Five batches, four to six solutions each. The author
  explicitly asks someone with more time and tokens to run it at scale.
- "Quality" was defined almost entirely by Opus, with only light steering on
  test quality. Deliberately so, to avoid the judge over-indexing on a supplied
  rubric, but it means the ranking reflects one model's taste.
- All tasks were greenfield, small to medium, and pure business logic. Nothing
  here speaks to large systems, legacy code, integration-heavy work, or work
  where the design is externally constrained.
- No run followed TDD perfectly, so the comparison is TDD-ish versus no TDD, not
  TDD versus no TDD.
- Single model family for generation. Nothing establishes that the result holds
  for other models.
- The mechanism explanation is a model's hypothesis about traces, generated
  after it had already ranked the solutions and then been told which was which.

## What would overturn this guidance

- A larger or better-controlled replication finding a design or
  mutation-score advantage for in-loop TDD. This is the direct refutation and
  the guidance should follow it.
- Evidence from non-greenfield or large-scale tasks that incremental TDD helps.
  This would not contradict the source at all, since it covers neither, and
  would add rows to the route table rather than removing them.
- Models that follow TDD instructions faithfully without heavy prompting. This
  removes the cost objection but leaves the core argument standing: a red step
  nobody reads is not evidence, and an agent that can emit test and
  implementation together feels no design pressure from ordering.
- A cheap, reliable way to detect tautological and weak assertions
  automatically. This would make agent-written tests trustworthy without the
  human checkpoint, which shifts where the human belongs but not the case
  against the ritual.
- Human-in-the-loop review at the test-review checkpoint (the article's usage
  pattern 2) turning out to be sustainable in practice at scale. The sensors
  article assumes it is not, on the grounds that reviewing unit tests is tedious
  enough that people will not actually keep doing it.
